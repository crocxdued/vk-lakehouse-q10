## 2. Поднятые сервисы — и почему именно они

Проверка: `docker compose ps -a` — `lakehouse-minio`, `lakehouse-pg`, `lakekeeper`, `trino` в статусе Up; одноразовые `lakehouse-minio-init`, `lakekeeper-migrate`, `lakekeeper-init` — Exited (0). Spark запускается по требованию в контейнере `tools`.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO (S3-совместимый форк `pgsty/minio`) | Объектное хранилище: три бакета `bronze`, `silver`, `gold`, в них физически лежат parquet/orc-файлы и метаданные Iceberg | Работает по протоколу S3, поэтому тот же стек без переделок переезжает в AWS S3 / Yandex Object Storage — меняется только endpoint. Хранилище отделено от вычислений: диск и движок масштабируются независимо. Официальный образ `quay.io/minio/minio` из гайда больше не скачивается (401), форк совместим по API. |
| PostgreSQL 17 | БД, в которой Lakekeeper хранит каталог: какие таблицы есть и какой metadata.json у каждой текущий | Каталогу нужна транзакционность: при двух одновременных коммитах в таблицу указатель на снапшот должен смениться атомарно, иначе таблица «потеряет» запись. Postgres — штатный бэкенд Lakekeeper, открытый и знакомый. |
| Lakekeeper | Iceberg REST Catalog: три warehouse `bronze`/`silver`/`gold`, каждый поверх своего бакета | Реализует открытый протокол Iceberg REST — к тем же таблицам подключаются Trino и Spark (это показано в п. 6.2) без копирования данных. Один лёгкий контейнер на Rust без JVM, в отличие от Hive Metastore; есть веб-UI для просмотра таблиц. Лицензия Apache 2.0. |
| Trino 476 | SQL-движок: метаданные берёт у Lakekeeper, данные читает и пишет в MinIO | Коннектор `tpch` генерирует данные на лету — ничего не скачивается. Iceberg-коннектор умеет CTAS, UPDATE/DELETE/MERGE, time travel, метатаблицы `$files`/`$snapshots`/`$partitions` и выбор формата/кодека на сессию — всё, что нужно для медальона и бенчмарка, делается на чистом SQL. |
| Spark 3.5 + Iceberg 1.9 (контейнер `tools`) | Второй движок: читает Bronze через тот же REST-каталог (п. 6.2), даёт сравнение Trino/Spark и опыт с кэшированием (лаба 2) | Подробно — в п. 6.2. |

### Скрипты, которыми поднимал стек

Вместо отдельных `docker run` из гайда весь стек описан в `docker-compose.yml`: те же образы и настройки, но порядок запуска контролируется `depends_on` (Lakekeeper стартует только после миграций и готового Postgres, Trino — после регистрации warehouse), и стек поднимается одной командой.

```bash
docker compose up -d        # minio            — S3-хранилище (порты 9000 API, 9001 консоль)
                            # minio-init       — создаёт бакеты bronze, silver, gold
                            # postgres         — БД каталога (5432)
                            # lakekeeper-migrate — миграции схемы каталога в Postgres
                            # lakekeeper       — Iceberg REST Catalog + UI (8181)
                            # lakekeeper-init  — принимает Terms of Use и регистрирует warehouse
                            #                    bronze/silver/gold (lakekeeper/warehouse-*.json)
                            # trino            — SQL-движок (8080), каталоги из trino/catalog/
docker compose ps -a        # проверка статусов
docker logs lakekeeper-init # для каждого warehouse — "warehouse-id"
docker exec trino trino --execute "SHOW CATALOGS"   # bronze, gold, silver, system, tpch

docker compose build tools  # Python + PySpark 3.5 + Iceberg 1.9 (tools/Dockerfile)
./run.sh all                # медальон, проверки, бенчмарк, Spark, отчёт
```

Каталоги Trino — `trino/catalog/{bronze,silver,gold}.properties` (как в гайде 2, но с именами сервисов `lakekeeper`/`minio` вместо `host.docker.internal` — контейнеры в одной сети compose) и `trino/catalog/tpch.properties`.

## 3. Разбор запроса — какие данные нужны

Q10 находит 20 клиентов, которые принесли больше всего выручки позициями, возвращёнными покупателем (`returnflag = 'R'`), из заказов IV квартала 1993 года. Выручка позиции — `extendedprice * (1 - discount)`.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `lineitem` | `orderkey`, `extendedprice`, `discount`, `returnflag` | фильтр `returnflag = 'R'`; джойн с `orders` по `orderkey`; агрегат `sum(extendedprice * (1 - discount))` |

## 4. Медальон — решения по каждому слою

Слои физически разделены, как в гайде 2: каталог Trino `bronze` → warehouse `bronze` в Lakekeeper → бакет `bronze` в MinIO (то же для silver и gold). SQL — `sql/01_bronze.sql`, `02_silver.sql`, `03_gold.sql`.
Строки — `count(*)`, вес — сумма `file_size_in_bytes` data-файлов из метатаблицы `"<таблица>$files"`. Формат везде PARQUET: колоночный стандарт для Iceberg и BI, а ORC в бенчмарке (п. 5) не дал выигрыша, который оправдал бы второй формат в стеке.

## 5. Тесты производительности

Методика (`./run.sh bench`, код — `tools/lab.py`): для каждой пары формат + кодек четыре нужные Q10 таблицы (`customer`, `orders`, `lineitem`, `nation`) пересоздаются из `tpch.sf1` в отдельной схеме `bronze.bench_<формат>_<кодек>`. Кодек задаётся сессией `bronze.compression_codec`. Время записи — серверное время CTAS по данным Trino. Размер — сумма `file_size_in_bytes` из `$files`. Q10 по этому Bronze выполняется 3 раз подряд; время — `elapsedTime` запроса из статистики Trino (то же, что в `system.runtime.queries`). Первый прогон считается отдельно (холодные кэши), для остальных берётся медиана. Всё на одной машине в Docker Desktop.

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | первый 8.22 с, далее медиана 11.47 с | 183.78 | Запись 97.04 с — на 24% медленнее ZSTD; размер на 3% меньше, повторный Q10 на 19% медленнее. GZIP (deflate) тратит больше CPU на сжатие; разумен для холодного архива, который пишут один раз и читают редко. |
| ZSTD | первый 5.27 с, далее медиана 9.67 с | 188.88 | Запись 78.46 с, размер на 3% больше GZIP, повторный Q10 на 16% быстрее. Сжимает почти как GZIP, но дешевле по CPU на записи — лучший баланс, поэтому ZSTD взят для слоёв медальона. |

Выводы из замеров:

- **Сжатие окупается по месту.** Bronze без сжатия — 488.66 МБ, самый компактный вариант (GZIP) — 183.78 МБ, в 2.7 раза меньше. Хранение, бэкапы и сеть до S3 оплачиваются по объёму, поэтому NONE в Bronze невыгоден.
- **Скорость записи:** быстрее всех PARQUET+ZSTD (78.46 с), медленнее всех PARQUET+NONE (100.13 с). Тяжёлый кодек платит CPU на записи; без сжатия экономится CPU, но на диск уходит больше байт.
- **Время Q10 зависит от варианта:** быстрее всего PARQUET+NONE (5.96 с), медленнее — PARQUET+GZIP (11.47 с): чем меньше байт читается из MinIO и чем дешевле распаковка, тем быстрее скан.
- **Trino vs Spark** (PARQUET+NONE): повторный Q10 в Trino 5.96 с, в Spark 1.38 с. Trino — MPP-движок с долгоживущим сервером и конвейерным выполнением, он рассчитан на интерактивные запросы; Spark платит за планирование стадий и запуск задач, его сила — большие батчевые ETL и ML, а не короткие запросы.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная реляционная БД держит данные на дисках одного сервера и оптимизирована под короткие транзакции; аналитика по миллиардам строк в ней медленная, а масштабирование — это покупка сервера побольше. Data lake решает проблему объёма: дешёвое объектное хранилище вместит сколько угодно файлов, но файлы — это не таблицы: нет транзакций, схемы, истории изменений, двое пишущих могут испортить данные. Lakehouse соединяет оба подхода: данные лежат в дешёвом S3 в открытых колоночных форматах (Parquet/ORC), а табличный формат Iceberg поверх них даёт ACID-коммиты, схему и её эволюцию, снапшоты и time travel. Хранение отделено от вычислений: одни и те же таблицы читают Trino, Spark и BI (в этой работе Trino пишет, Spark читает те же файлы), а движок можно сменить или масштабировать, не перенося данные. Колоночное хранение и сжатие делают аналитику дешёвой: из 16 колонок `lineitem` Q10 читает 4. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | На `silver.lakehouse.dim_customer` (`./run.sh evolution`, шаги — `sql/05_evolution_timetravel.sql`, часть A). Исходно 9 колонок. `ADD COLUMN customer_tier varchar` выполнился мгновенно: из 150 000 строк заполнено 0 — у старых строк NULL, потому что Iceberg записал только новую версию схемы в metadata.json, а parquet-файлы не переписывал. Затем `UPDATE` заполнил колонку по балансу клиента: DEBTOR — 13 692, HIGH — 67 989, REGULAR — 68 319. `RENAME COLUMN phone TO phone_number` — `DESCRIBE` сразу показал новое имя, данные читаются по-прежнему (например, 25-989-741-2988): Iceberg сопоставляет колонки по числовому id, а не по имени, поэтому переименование не ломает старые файлы. Потом имя вернул, чтобы `03_gold.sql` работал. По `$snapshots` видно: `ADD COLUMN` и `RENAME` не создали новых снапшотов — это изменения только метаданных; снапшот появился только от `UPDATE`, который реально записал данные. |
| Пример скрипта восстановления данных из снапшота (time travel) | Часть B того же скрипта. Снапшот до аварии S0 = `6194548103525278235`. «Авария»: `DELETE FROM silver.lakehouse.dim_customer WHERE region = 'EUROPE'` — клиентов региона было 30 197, стало 0. Чтение прошлого: `SELECT count(*) FROM silver.lakehouse.dim_customer FOR VERSION AS OF 6194548103525278235 WHERE region = 'EUROPE'` → 30 197. Восстановление: `INSERT INTO silver.lakehouse.dim_customer SELECT * FROM silver.lakehouse.dim_customer FOR VERSION AS OF 6194548103525278235 WHERE region = 'EUROPE'` → снова 30 197, всего в таблице 150 000. Возвращены только потерянные строки, а не вся таблица, и история сохранена для аудита: append → overwrite → delete → append. |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Apache Spark 3.5 + Iceberg 1.9 (движок) | Trino уже закрывает интерактивный SQL, поэтому второй MPP-движок того же класса (Doris, StarRocks) дублировал бы его роль. Spark — движок другого типа: батчевые ETL, DataFrame API на Python, ML. Он подключается к тому же Iceberg REST-каталогу Lakekeeper и читает те же файлы в MinIO без копирования — это и есть главное обещание lakehouse (одни данные — много движков). Кроме того, Spark нужен лабе 2: на одних и тех же файлах можно сравнить два движка и показать влияние кэша (`CACHE TABLE`). Для моей задачи (короткий агрегирующий запрос) Trino быстрее, а Spark был бы лучше для тяжёлой пересборки слоёв на больших объёмах. |

Развёртывание — сервис `tools` в `docker-compose.yml` и `tools/Dockerfile` (Python 3.12, OpenJDK 17, `pyspark==3.5.6`, jar-файлы `iceberg-spark-runtime-3.5_2.12` и `iceberg-aws-bundle` 1.9.2). ## 8. Лабораторная 2 — форматы, метаданные, кэширование

Мои параметры из таблицы преподавателя: формат **PARQUET**, сжатие **NONE**. Все замеры — на том же стенде, тем же Q10 в качестве агрегации.

**Строка для таблицы:**

| Сжатие | Формат | Размер, ГБ | Файлов | Время записи, с | Агрегация первая, с | Агрегация вторая и следующие, с | Тест | Trino | Spark |
|---|---|---:|---:|---:|---:|---:|---|---|---|
| none | parquet | 0.3495 | 4 | 76.432 | 3.61 | 5.96 | sf1 | 3.61 / 5.96 | 5.52 / 1.38 |

Размер, файлы и время записи — таблица `lineitem` (основной объём данных). Агрегация — Q10 в Trino: первая — сразу после перезапуска Trino (холодный кэш метаданных), вторая и следующие — медиана повторных прогонов. Колонки Trino/Spark — «первый / повторный» прогон в каждом движке.

### 8.1. Влияние объёма метаданных (много мелких файлов)

Те же данные (PARQUET+NONE) записаны второй раз с `target_max_file_size = 8MB` — файлов становится больше, каждый меньше.

| Вариант | Файлов всего | Файлов lineitem | Манифестов | Манифесты, КБ | Размер, МБ | Запись, с | Планирование Q10, мс | Q10 далее, с |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| обычные файлы | 8 | 4 | 4 | 30.9 | 488.66 | 100.13 | 339 | 5.96 |
| мелкие файлы (8MB) | 83 | 61 | 4 | 41.0 | 485.23 | 127.86 | 605 | 12.89 |

Файлов `lineitem` стало в 15 раз больше. Чем больше файлов, тем больше записей в манифестах: движку при планировании нужно прочитать метаданные, отобрать файлы и раздать их как splits, а на чтении — открыть каждый файл отдельным запросом к S3 и прочитать его футер. Q10 на мелких файлах: 12.89 с против 5.96 с (на 117% медленнее). Объём данных при этом почти тот же (485.23 против 488.66 МБ) — платим не за байты, а за число объектов и метаданных. Отсюда практическое правило: файлы в lakehouse держат крупными (сотни МБ), а мелкие периодически уплотняют (`ALTER TABLE ... EXECUTE optimize`).

### 8.2. Кэширование

| Сценарий | Время, с |
|---|---:|
| Trino, первый Q10 сразу после записи | 9.90 |
| Trino, повторные Q10 (медиана) | 5.96 |
| Trino, первый Q10 после `docker compose restart trino` | 3.61 |
| Trino, второй Q10 после рестарта | 1.75 |
| Spark, первый Q10 (новая сессия) | 5.52 |
| Spark, повторные Q10 (медиана) | 1.38 |
| Spark, заполнение `CACHE TABLE` нужных колонок | 5.42 |
| Spark, Q10 по закэшированным данным (медиана) | 1.21 |

Первый запрос всегда дороже: движок загружает метаданные таблиц из каталога (metadata.json, манифесты), JIT-компилятор JVM ещё не разогнал код операторов, а файлы не лежат в страничном кэше ОС контейнера MinIO. После рестарта Trino кэши метаданных и JIT обнуляются — поэтому первый прогон снова медленный, а второй быстрый. В Spark то же плюс запуск задач; явный `CACHE TABLE` держит нужные колонки в памяти исполнителя, и запрос больше не ходит в S3 — это выгодно, когда одни данные читаются много раз подряд, но стоит памяти и времени на заполнение кэша.

### 8.3. Компромисс «размер ↔ скорость ↔ стоимость»

Мой вариант PARQUET+NONE: 488.66 МБ, запись 100.13 с, повторный Q10 5.96 с. Самый компактный — PARQUET+GZIP: 183.78 МБ, запись 97.04 с, Q10 11.47 с. Хранение моего варианта обойдётся в 2.7 раза дороже (плата за объём в S3 и трафик пропорциональна размеру), а по скорости повторного Q10 мой вариант на 48% быстрее. Поэтому без сжатия имеет смысл держать разве что короткоживущие промежуточные данные, которые много раз читаются CPU-ограниченным движком; для Bronze/Silver/Gold — ZSTD, для холодного архива — GZIP или ZSTD с высоким уровнем, для горячих данных с частой перезаписью — SNAPPY.
